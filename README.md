# Цифровой двойник клиента с адаптивной импутацией — MVP

Рабочий прототип идеи из «Практической работы 1»: ML строит виртуальную копию клиента,
достраивает недоступные данные **с честной оценкой неопределённости** и либо выдаёт оффер,
либо отказывается и просит данные.

Домен в демо — автострахование (КАСКО): клиент, телематика, партнёрские данные, договор.
Домен меняется правкой одного файла `js/data.js` (реестр признаков + сценарии).

---

## Как запустить

**Вариант 1 — просто открыть файл.** Двойной клик по `index.html`. Внешних зависимостей нет,
всё считается в браузере.

**Вариант 2 — локальный сервер (рекомендуется для показа):**

```powershell
node serve.cjs 4173
# затем открыть http://127.0.0.1:4173/
```

Есть `package.json` без зависимостей: `npm start` запускает тот же сервер на 4173.

Требуется любой современный браузер (Chromium/Firefox/Safari). Node нужен только для сервера и тестов.

Диплинки для показа сразу нужного состояния:
`#twin/consent`, `#twin/api`, `#impute/consent`, `#feedback/consent/revealed`, `#risks/adversarial`,
`#profile/full/new` (сразу открывает окно создания клиента).

## Как создать своего клиента

Клиент больше не захардкожен — его можно завести прямо в интерфейсе.

1. В левом рельсе, в карточке клиента, нажмите **«＋ новый клиент»**.
2. В открывшемся окне три пути:

   * **готовые персоны** — «Молодой водитель» (24 года, новый автомобиль, 8 тыс. км),
     «Курьер» (29 лет, 40 тыс. км/год, был отказ по телематике), «Опытный, полный стаж»
     (52 года, стаж 9 лет), «Пенсионер» (68 лет, 6 тыс. км), «Новый клиент без истории»;
   * **«Случайный из популяции»** — сэмпл из тех же 2 400 клиентов, на которых учится импутация;
   * **ручной ввод** — все 14 признаков в одном окне. Под каждым полем подписано среднее
     по популяции (μ) и границы признака, а валидатор сразу предупреждает об осмысленных
     несоответствиях: «автомобиль старше, чем позволяет возраст водителя»,
     «пробег выше 60 тыс. км/год — край популяции, интервал будет широким», «больше 5 обращений».

   В отдельном поле — **история отказов** (нет / один отказ / повторные): именно она включает
   adversarial-детектор, поэтому на своём клиенте его тоже можно проверить.

3. **«Применить и пересчитать»** — новый клиент заменяет текущего: пересчитываются карта
   доступности, импутация, симуляция двойника и цена. Созданный клиент сохраняется в localStorage
   и не теряется при перезагрузке; вернуть демо-клиента А. Волкова — кнопка
   **«вернуть демо-клиента»** в карточке клиента.

Важно: значения, которые вы вводите, — это «истинные» данные клиента. Их же раскроет шаг
«Данные пришли», поэтому петля обратной связи на своём клиенте покажет честную ошибку именно
ваших значений, а не заранее заготовленную.

Правка в коде (если так удобнее): `js/data.js` → `D.DEFAULT_SPEC` (демо-клиент), `D.PRESETS`
(персоны), `D.makeClient(spec)` (фабрика: принимает любые из 14 полей, обрезает в допустимые
границы, собирает подпись и историю).

## Пять экранов = пять тезисов идеи

| Экран | Что показывает | Тезис из работы |
|---|---|---|
| **Профиль** | карта доступности 14 признаков в 5 слоях; статусы «получено / отсутствует / устарело / запрещено», у каждого пропуска тип **MCAR / MAR / MNAR** | «не просто null, а типизированная пропущенность» |
| **Импутация** | MICE (ridge, 3 итерации, B = 20 бутстрэп-цепочек): значение, σ, 90 % ДИ, уверенность, применённый сдвиг приора | «на выходе не пробег = 15 000, а 15 000 ± 4 000, уверенность 0,7» |
| **Digital Twin** | Monte Carlo по ансамблю профилей × 3 варианта договора: цена, E[выплата], убыточность, P(покупки), E[прибыль], разброс | «двойник получает распределение, а не точку» |
| **Обратная связь** | импутация против факта: MAE, смещение, покрытие 90 % ДИ, недобор цены; перекалибровка MNAR-сдвига на отложенной выборке | «модель импутации дообучается, когда данные приходят» |
| **Риски и аудит** | 6 рисков с *живыми* метриками + контрмеры-переключатели + журнал решений и выгрузка протокола | «ложная уверенность, каскад, adversarial, прокси-дискриминация» |

Сценарии доступности данных (переключаются в левом рельсе):

| Сценарий | Что сломано | Итог решения |
|---|---|---|
| Полный профиль | только публичный слой устарел | **оффер**, разброса нет (профиль известен точно) |
| Партнёры молчат | банк/телеком не ответили (MAR), доход запрещён | **оффер**: пропуски MAR в признаках, не входящих в модель риска, — не повод отказывать |
| Внешние API упали | район и состояние авто (MCAR, оба влияют на тариф) | **условный оффер** с надбавкой за неопределённость |
| Нет согласия на телематику | пробег, торможения (MNAR), ночные поездки (MAR) | **запрос данных**: ключевой признак восстановлен с уверенностью 10 % |
| Adversarial-пропуски | 6 пропусков + повторные отказы | **запрос данных** + флаг детектора, сдвиг приора усилен |

## Как устроена логика

### 1. Типизированная пропущенность
У каждого пропуска есть тип, и от него зависит **право** заполнения и ширина интервала:

* `MCAR` — σ × 1,00, без сдвига приора;
* `MAR` — σ × 1,12 (ковaриаты учтены, но остаточная неопределённость выше);
* `MNAR` — σ × 1,50 **+ сдвиг приора вверх** (пробег × 1,18, торможения × 1,12) и скидка уверенности 10 %;
* чувствительные признаки (доход) — импутация **запрещена**, только ручной запрос.

**Уверенность поля** — это не «качество модели», а вероятность:
`P(восстановленное значение останется в коридоре допуска)`.
Коридор — `±0,60σ` для ключевого признака, `±0,75σ` для среднего, `±1,00σ` для второстепенного,
где σ — разброс популяции **в шкале модели** (для скошенных величин — в логарифмах). Скидки:
×0,9 при MNAR (сам сдвиг приора — догадка), ×0,9 при adversarial-флаге.
Уверенность профиля — взвешенное геометрическое по признакам: «вероятность, что весь профиль
остался в допуске».

> **Про масштаб.** Раньше уверенность считалась как `0,97 − 0,62·(σ/σ_популяции) − штраф`,
> причём σ бралась в исходных единицах. Для логнормального пробега любое честное распределение
> даёт σ/σ_популяции > 1 (коэффициент вариации ≈ 0,5), поэтому формула упиралась в пол 0,10
> **у любого клиента** — метрика перестала различать профили. Теперь σ и коридор считаются
> в одной шкале (лог), и число снова осмысленно: тот же скрытый пробег даёт 26 % как MNAR,
> 38 % как MAR и 42 % как MCAR.

### 1.1. Почему у скрытого пробега уверенность около 25 %
Модель объясняет только **16 % разброса пробега** по известным признакам (R² = 0,16, проверено
на отложенной выборке). Это значит, что честный интервал обязан быть широким: ±50 % и больше
после MNAR-сдвига. 25 % — это не сбой и не плохой профиль клиента, а честное «про пробег этого
клиента мы знаем почти столько же, сколько среднее по популяции».
Чтобы это было видно, рядом с каждым заполненным признаком в интерфейсе показаны **коридор
допуска** и **R²** — на чём именно стоит число. Пробег предсказывается плохо (R² 16 %), состояние
авто и скоринг — лучше, поэтому у них уверенность выше при той же «силе» пропуска.

Чтобы получить высокую уверенность по пробегу, нужны признаки, реально с ним коррелирующие
(заявленный годовой пробег из анкеты, рабочий адрес, число поездок), — сейчас в синтетической
популяции их нет, и это ограничение модели, а не баг расчёта.

### 2. Импутация (MICE + бутстрэп)
20 бутстрэп-цепочек по 3 итерации, в каждой итерации ridge-регрессия признака по остальным,
отдельно обучаемая на пересэмплированной обучающей выборке (2 400 синтетических клиентов).
Каждая цепочка после сходимости получает остаточный шум → на выходе **20 полных профилей**,
а не 20 повторов среднего. Это и есть «распределение»: оно же уходит в двойник как ансамбль
миров, поэтому корреляция между признаками сохраняется.

Защита от экстраполяции: предикторы обрезаются по ±3σ, значения — по перцентилям 0,5–99,5.

### 3. Digital Twin
Для каждого из 20 профилей считается ожидаемая выплата (логика частоты × тяжести,
франшиза по каждому случаю, стекло, угон/стихия как ожидаемая стоимость) и цена из риск-множителей.
Дальше 1 400 симуляций профиля × 3 договора:

`прибыль = цена × 0,84 − 2 400 ₽ привлечения − ожидаемая выплата`, взвешенная на `P(покупки)`;
`P(покупки) = σ((выгода покрытия × склонность к риску − цена) / 5 400)`.

Склонность к риску и «вкус» зафиксированы как **свойства клиента**, а не броска — иначе разброс
решения был бы потребительским шумом, а не следствием неопределённости профиля.

### 4. Порог и гейт (то самое «где я знаю, а где предполагаю»)
```
уверенность решения = 0,65 × уверенность импутации + 0,35 × устойчивость выбора варианта
гейт: если ключевой (core) признак восстановлен с уверенностью < 45 % → не оффер, а запрос данных
      ≥ 86 % → оффер · ≥ 62 % → условный оффер с надбавкой за неопределённость · иначе запрос
```
Core-признаки: возраст водителя, возраст авто, стаж, обращения, **пробег**.
Именно поэтому сценарий с телематикой не доходит до оффера, хотя устойчивость выбора варианта
у него 71 %: система отказывается опираться на *предположение* о ключевом риске.

### 5. Ценность запроса данных
Для каждого пропуска считается Δ уверенности, если признак станет известен (усреднение по
20/50/80 перцентилям его апостериорного распределения). Список запросов сортируется по этому Δ —
«что спросить» определяется влиянием на решение, а не важностью признака в вакууме.

### 6. Обратная связь
Раскрытие фактов даёт MAE, систематическое смещение, покрытие 90 % ДИ и контрфактическую цену
(сколько компания недобрала из-за заниженного пробега). Перекалибровка MNAR-сдвига оценивается
на 120 отложенных клиентах, у которых признак спрятан по MNAR-механизму: коэффициент =
`Σфакт / Σимпутация`, и это уменьшает смещение при сохранении покрытия.

### 7. Контрмеры — живые, а не декоративные
Переключатели на экране «Риски» реально меняют поведение системы:

* **порог уверенности / core-floor** — выключить → оффер выдаётся на признаке с уверенностью 10 %;
* **ансамблевая симуляция** — выключить → остаётся одна «истина»: разброс исчезает,
  уверенность искусственно растёт (демонстрация ложной уверенности);
* **запрет импутации чувствительных** — выключить → доход начинает заполняться;
* **логирование / fairness-аудит** — управляют журналом и проверкой прокси-связей.

## Сценарий демонстрации (4–5 минут)

Кнопка **«Дальше →»** в левом рельсе (или →) ведёт по пяти шагам. Числа ниже — для демо-клиента
А. Волкова; после создания своего клиента цифры будут другими, а логика шагов та же.

1. **Полный профиль** → экран «Профиль». Карта доступности: почти всё получено, стоп-кадр «здесь
   система знает». Перейти на «Digital Twin»: оффер, разброса нет. Ремарка: разброс возникнет,
   когда профиль перестанет быть точным.
2. Переключить сценарий **«Нет согласия на телематику»** → «Профиль»: три пропуска, у пробега и
   торможений тип **MNAR**. Отметить: это не «нет данных», а «скрыто, и скрыто не случайно».
3. **«Импутация»**: пробег восстановлен ≈ 17,8 тыс. км с ДИ 6,9–51,8 тыс. и уверенностью 25 %;
   рядом — коридор допуска 10,8–18,4 тыс. км и R² 15 %: видно, что цифра низкая потому, что
   известные признаки почти не объясняют пробег. Ниже — что без сдвига приора было бы ещё меньше.
   Показать запрет на доход.
4. **«Digital Twin»**: баннер «Нужны данные» — гейт остановил оффер на core-признаке. Ниже —
   таблица «что даст запрос» (топ-1 — пробег) и разложение цены: 29 % цены построено на
   предположениях. Нажать **«запросить»** у пробега → система пересчитывается, оффер появляется.
   (Отменить: «Сброс».)
5. **«Обратная связь»** → «Данные пришли →»: точечная оценка была занижена на 30 %, а факт хотя и
   попал в 90 % ДИ, но интервал шириной ×8 — то есть «честный», но бесполезный для цены.
   Недобор цены ≈ 12,6 тыс. ₽. Нажать **«Перекалибровать MNAR-сдвиг»**: смещение на валидации
   уходит с −15 % до +6 %, оценка пробега подтягивается с 17,8 до 22,3 тыс. км (факт 26,4).
   MAE на валидации при этом слегка растёт (19,6 % → 22 %) — честная плата за устранение
   систематического смещения.
6. **«Риски и аудит»**: шесть рисков с цифрами; выключить «порог уверенности» и «ансамблевую
   симуляцию» — показать деградацию; включить обратно. Журнал + «выгрузить протокол» (JSON).

## Что в MVP сознательно упрощено

* Данные **синтетические** (2 400 обучающих + 120 отложенных клиентов); реального датасета и
  обученной на истории модели нет. Импутация считается честно, но на сгенерированном мире.
* Одна таблица риска вместо актуарной модели; тяжесть убытка — смесь двух логнормалей.
  Угон и стихия учтены как ожидаемая стоимость, стекло — стохастически.
* Surface-уровень «как это выглядит для продукта»: нет авторизации, сохранения состояния,
  A/B, интеграций и реального API-слоя.
* Устойчивость решения измеряется по ансамблю импутации (20 цепочек), поэтому метрика
  дискретна (шаг 5 %) — для показа этого достаточно, для продакшена нужен больший B.

## Куда развивать дальше

1. Заменить синтетику на исторические данные и обучить MissForest/XGBoost-импутер,
   оставив интерфейс политик тем же.
2. Добавить байесовские интервалы (Gaussian Process / квантильная регрессия) вместо
   бутстрэп-разброса и откалибровать покрытие на реальных «пришедших» данных.
3. Считать ожидаемую ценность информации с учётом **стоимости** запроса (сколько стоит
   телематика против прироста уверенности) — сейчас ранжирование по Δ уверенности.
4. Свести fairness-аудит к регулярному отчёту: доля решений на импутированных данных,
   их фактическая убыточность, прокси-корреляции по всем чувствительным атрибутам.
